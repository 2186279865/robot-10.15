# new_eye 双 USB 相机视觉项目交接文档

## 1. 项目目标

本项目用于工创赛智能分拣装置的视觉识别。当前硬件条件为：

- 两个 USB 摄像头；
- XYZ 龙门架；
- 三爪柔性夹爪，夹爪不能旋转；
- 底部旋转托盘。

由于夹爪抓起物料后会遮挡物料，系统要求在抓取前完成识别。抓取后只允许做夹持状态、入盒状态等确认，不再依赖物料识别。

## 2. 当前视觉方案

当前主识别链为：

```text
顶视相机实时画面
→ 四点区域定位
→ 透视校正
→ SAM 自动实例分割
→ 独立目标掩膜和外接框
→ 输出目标中心、外接框和置信度
→ 后续再接类别聚类和龙门坐标转换
```

当前没有使用传统阈值分割作为主识别方法。`vision.py` 中仍保留旧的颜色和几何分割函数，但 `gui.py` 的“单次识别”入口使用 `auto_segment.py` 的 SAM 后端。

## 5. 窗口使用流程

程序会自动读取 `config.json` 并尝试打开上次使用的两台摄像头。

### 顶视相机

顶视相机负责主识别和抓取坐标。点击“顶视四点框选”，然后按以下顺序点击：

```text
左上 → 右上 → 右下 → 左下
```

绿色四边形表示有效识别区域。右键可以撤销上一个点。

### 副摄相机

副摄相机可以独立旋转、缩放和平移，也可以点击“副摄四点框选”完成四点定位。目前副摄主要用于辅助观察，主识别仍来自顶视相机。

### 旋转和保存

每路画面都有左转 90°、右转 90°和复位按钮。调整完成后点击“保存配置”，下次启动会恢复：

- 顶视和副摄索引；
- 顶视和副摄旋转角度；
- 顶视和副摄四点坐标；
- 当前类别映射和模型路径。

### 识别

四点定位完成后点击“单次识别”。识别框会直接叠加到顶视实时画面上，不再使用右侧黑色轮廓窗口。

结果写入：

```text
new_eye\runtime\latest_targets.json
```

## 6. SAM 识别流程

`auto_segment.py` 使用 Ultralytics SAM：

1. 对四点区域透视校正后的图像推理；
2. 在图像内生成网格正点提示；
3. 获取每个候选掩膜；
4. 过滤过小、过大的区域；
5. 使用 IoU 和包含关系去除重复掩膜；
6. 输出掩膜、轮廓、外接框、中心点和置信度。

识别结果中：

- `bbox_warped`：透视校正图中的外接框；
- `bbox`：转换回原始顶视实时画面的外接框；
- `center_px`：目前是透视校正图中的中心点；
- `confidence`：当前 SAM 结果的基础置信度，后续应增加真实质量评分；
- `class_name`：当前为“待聚类”，还没有完成未知物料自动分成 1～6 类。

## 7. 当前已知问题

### 7.1 未知物料分类还没有完成

SAM 只负责“有几个物体、每个物体边界在哪里”，不能直接判断物料类别。后续需要在 SAM 掩膜基础上增加：

- 颜色特征；
- 轮廓和几何特征；
- 表面文字、二维码或图案特征；
- DINOv2/CLIP 特征；
- 最多 6 类的现场聚类。

### 7.2 SAM 网格提示可能重复

同一个物料可能生成多个候选掩膜。当前通过 IoU 和包含比例去重，但仍需要用真实物料画面测试。若仍然重复，应进一步使用：

- 更稀疏的正点网格；
- 只在四点区域内提示；
- 掩膜面积和中心距离聚类；
- 对同一目标只保留最高质量掩膜。

### 7.3 坐标标定尚未接入

当前仍然是：

```json
"motion_authorized": false,
"calibration_status": "missing"
```

不能直接让识别结果驱动龙门架。必须完成：

- 相机到托盘平面标定；
- 像素到毫米转换；
- XYZ 原点和行程限制；
- Z 轴安全高度和抓取高度；
- 夹爪中心偏置；
- 储物盒坐标。

### 7.4 两台相机并未融合

目前副摄只用于显示和辅助定位，主识别使用顶视相机。后续如需融合，应通过同一物料的时间和坐标关系，把副摄特征合并到顶视目标，而不是简单拼接两张图。

## 8. 后续推荐开发顺序

1. 先用真实托盘和物料确认 SAM 是否能做到“一件物料一个掩膜”；
2. 在顶视实时画面上修正重复框和漏检；
3. 增加每个目标的轮廓面积、颜色直方图和形状特征；
4. 加入 DINOv2 或 CLIP 特征，完成最多 6 类自动聚类；
5. 增加目标置信度门限，低置信度目标禁止抓取；
6. 完成相机到龙门坐标标定；
7. 接入抓取前状态机；
8. 增加夹爪夹持确认和储物盒入盒确认；
9. 最后才将 `motion_authorized` 从 `false` 改为受控授权。

## 9. 推荐的抓取状态机

## 11. 重要注意事项

- 四点顺序必须保持一致：左上、右上、右下、左下；
- 相机、托盘和四点区域建立后不要随意移动；
- 改变旋转角度、相机位置或光照后，应重新检查四点和识别结果；
- 不要在未完成坐标标定时接入机械运动；
- 当前识别结果只代表视觉候选，不代表已经抓取成功；
- 比赛正式规则和评分以最新官方文件为准。

## 12. 2026-10-18 更新：实时分割 / 去误检 / 双摄融合

- **实时分割**：`gui.py` 底部“实时分割”按钮，后台线程持续取两路最新帧 → 四点透视校正到 700×700 → SAM 实例分割 → 画面持续叠加“黄轮廓 + 黄框 + 红十字 + #编号”。状态栏和顶视画面左上角显示：刷新帧率、两路相机帧率、分割帧率、双摄目标数。
- **去误检（空处不再报目标）**：`auto_segment.py` 不再用 5×5 网格盲打点。先用颜色（饱和度>45）或“与空托盘的灰度差”找候选前景块，只在候选块内部撒提示点；空托盘、阴影、反光没有候选 → 不会产生提示 → 不会出现假目标。掩膜再按面积、贴边、候选占比、物体性（饱和度/差分亮度）过滤并去重。灰/黑物料需勾选“含灰/黑物料”（config `gray_objects: true`），并建议先“采集空托盘”。
- **双摄融合**：新增 `fusion.py`。顶视负责俯视位置/轮廓/数量；副摄在同一 700×700 托盘坐标系里按水平位置 u 印证顶视目标（同一列前后重叠的物体允许共用一块侧影，副摄分不出前后深度），副摄多出来的目标作为 `side` 目标追加（常见于顶视被遮挡）。两路左右方向相反时自动翻转对应关系。融合结果保留顶视 bbox/中心点，副摄信息作为附加字段。
- **输出 JSON**：`schema_version` 升到 4，每个目标新增 `views`（`top+side`/`top`/`side`）、`id`；双摄都看到时附带 `side_bbox`、`side_center_px`、`height_ratio`（副摄框高/700，仅作高度特征）。`motion_authorized` 仍恒为 `false`。
- **已知限制**：SAM 只做实例分割不分类（`class_id`/`class_key` 仍为占位）；副摄不做三维定位；副摄画面里被裁切/贴边的物体可能不参与融合；当前帧率约 0.4~1.5 fps（GPU 0.66 s/帧单路），实时性靠“后台持续检测 + 画面刷新”而不是高帧率推理。

## 13. 2026-10-18 更新：规则特征分类 + 现场样本登记

- **方法（不训练模型，用户定案“规则特征 + 现场登记”）**：新增 `new_eye/classify.py`。在 SAM 掩膜上算两类特征：
  - 颜色：掩膜先腐蚀（`min(h,w)*0.12`，去掉边缘/高光/阴影），剔除 `V<35` 和 `V≥250` 的像素，取 HSV 中值 → `黑 / 浅色/白 / 红 / 黄/橙 / 绿 / 蓝/浅蓝 / 紫/其他`，附带纯度置信度与 12+4+4 维 HSV 直方图；
  - 形状：`cv2.approxPolyDP(0.035*peri)` 顶点数（3/4/5 → 三棱/正方或长方/五棱），圆度>0.80 且实心度>0.93（或顶点≥6 且圆度>0.74 且面积占比<0.84）→ `圆柱/圆形`；圆顶面若副摄侧影顶部收窄 `side_curv<0.78` → `球`；其余 `其他几何体`；
  - 特征向量 = HSV 直方图 + 7 维 Hu 矩 + 形状量（圆度/长宽比/顶点数/实心度/面积占比/侧影收窄）归一化，用于同键不同物时的余弦最近邻（阈值 `sample_similarity=0.88`）。
- **类别映射**：键是 `形状|颜色`，查序：`config.class_map`（来源 `rule`）→ `samples.json` 同键（`sample-key`）→ 特征最近邻（`nearest`）→ 都没有则 `class_name="待登记"`、`class_source="unknown"`、`need_review=true`（不硬猜）。用户规则要求“形状相同且颜色相同 → 同一储物盒”，初赛 ≥12 件、≥6 类，因此最多 6 类、键空间有限。
- **现场登记**：GUI 底部“登记样本”按钮 → 再点顶视画面里的目标 → 弹窗输入类别编号或名称。`classify.register()` 把特征存 `new_eye/samples.json`（同类别重复样本按余弦>0.985 去重），同时把 `形状|颜色` 写回 `config.json` 的 `class_map` 并把名字写 `class_names`；立即 `save()` 持久化，重启后规则映射仍有效。副摄单独看到的目标（side-only）不能登记，只标“副摄待确认”。
- **接线**：`gui.py` 的 `detect_and_fuse()` 融合后调用 `classify_fused()`；实时分割每帧也做分类（耗时可忽略），状态栏显示 `类别1×2 类别3×2 …`，画面标签显示 `#id 类别名`，框线颜色按类别区分（6 色调色板）；`recognize()` 用 `frames_for_vote` 帧投票，同位置目标的 `class_key/shape/color` 取多数，投票结果记入 `class_votes`（如 `5/5`）。
- **输出 JSON**：`schema_version` 升到 5，顶层新增 `class_summary`、`max_classes`、`classification_logic`；每个目标新增 `shape`/`shape_conf`、`color`/`color_conf`、`class_id`/`class_name`/`class_key`/`class_conf`/`class_source`、`need_review`、`class_votes`。`motion_authorized` 仍恒为 `false`。
- **实测（crop_test.jpg 5 物体，合成副摄影像）**：5 个目标全部 `top+side`；分类结果 `圆柱/圆形|黄/橙`×2 → 类别1、`五棱体|绿` → 类别2、`圆柱/圆形|红`×2 → 类别3；`det_fps≈0.56`；截图 `new_eye/runtime/classify_proof.png`（1450×850）。
- **已知限制**：六棱柱可能被归入“圆柱/圆形”（`extent<0.84` 兜底会误收），登记时核对；同色同形但需要区分大小/高度的物体，规则特征无能为力，得靠登记样本的最近邻或后续加尺寸特征；颜色在强反光/暖光下会漂移；副摄 side-only 目标只给颜色不给类别。

## 15. 2026-10-18 更新：每步耗时、副摄隔帧、双摄一致性

### 15.1 右侧面板新增【耗时】（`gui.py` 的 `_panel_text()`，数据来自 `App.times`）
- 计时点：`detect_targets(frame, which, stats)` 里量三段 `校正(warp)/分割(SAM)/反投影(contour→原图)`；`detect_and_fuse()` 量 `融合(fuse)/分类(classify)/核心(core)`；`live_loop` 量 `写JSON(write)` 和 `整帧(frame)`（`recognize()` 也会记 `frame`）。
- 平滑：`App._merge_times(st)` 对每个 key 做 EMA（系数 0.6），避免单帧抖动；面板显示 3 行：
  `【耗时】整帧 1.00s   顶视 764ms（分割 744ms）` / `顶视细分：校正 4ms / 分割 744ms / 反投影 16ms` / `副摄 766ms（分割 750ms）  融合 0ms  分类 17ms  写JSON 1ms`。
- 实测（crop_test + 合成副摄，GPU/CPU）：SAM 分割是绝对大头（顶视 ~74%，副摄同量级），分类 ~17ms、融合 <1ms、写 JSON ~1ms。

### 15.2 副摄隔帧复用（`side_every`，默认 2）
- `live_loop` 调 `detect_and_fuse(fr, side_fr, int(cfg.get('side_every', 2) or 1))`：副摄每 N 帧跑一次 SAM，其余帧直接用 `self.side_cache` 的上一份副摄结果与 warp。
- 实测整帧 1.46s → 1.00s，实时分割 0.53 → 0.98 fps。`cfg['side_every']=1` 可关掉复用。

### 15.3 同一物体在两路被标成两类 —— 原因与修法（**已被第 16 节的严格一对一替换**，保留作历史记录）
原因有两个叠加：
1. 副摄只能看到水平方向 u，**同一列（同一 u、不同 v）的多个顶视目标会共用同一块副摄侧影**；旧代码按遍历顺序把这块侧影的标签写成“第一个用它”的顶视目标的类别，于是同一块侧影上可能出现另一个物体的类别名，看起来就是“一个物体两个类”。
2. 旧融合只按 |Δu| 配对，不同颜色的两列物体可能被错配（比如黄色的顶视目标配上红色的侧影），标签跟着错。
修法：
- `fusion.py`：匹配打分改为 `score = |Δu| + 颜色惩罚`（`_color_penalty`：两路颜色一致 0、未知 0.03、明显不同 0.10），即优先把同色目标配到一起，但门限仍按 |Δu|≤0.18 控制；每个融合项新增 `dist`（实际 Δu）和 `color_mismatch`（两路颜色明显不一致）。
- `fusion.py::fuse()` 现在返回 `flip`，`fuse()` 里记录 `dist`/`color_mismatch`；`gui.py::write_targets()` 输出新增 `color_mismatch`，`need_review` 合并该标志。
- `gui.py::draw_targets()`：副摄侧影按 `id(side_item)` 分组，**每块侧影只画一次**，标签取 `dist` 最小的顶视目标，被 N 个顶视目标共用时标 `×N`。
- `_panel_text()`：`#id 类别名` 后面加 `⚠两路颜色不一致`；类别统计把 `副摄待确认` 拆出来显示为 `未确认×N`，不再混进类别里。


## 16. 2026-10-18 更新：严格一对一融合、识别耗时日志

### 16.1 单次识别 / 实时停止都报告耗时
- `App.recognize()`：从点击开始计时到写 JSON 结束，日志输出一行（时间戳照旧保留）：
  `17:02:13  单次识别完成：5 个目标（顶视5/副摄0，2 帧投票），用时 2.51s（顶视 2.31s / 副摄 0.00s / 融合 0.00s / 分类 0.03s / 写JSON 0.00s）| 类别统计`
  各阶段是本次 n 帧投票的**累计值**（`detect_and_fuse(..., stats_out=[])` 收集每帧 stats 后相加）。
- `App.stop_live()`：累计实时帧数与总耗时，停止时输出 `实时分割已停止：12 帧，平均 1.29s/帧（约 0.77 fps）`；从“停止”按钮进 `stop()` 时也会先走这条日志。
- 面板【耗时】仍显示 EMA 平滑后的**单帧**各阶段耗时，两者互补。

### 16.2 融合改成严格一对一（修“同一物体两路两个类”）
- 根因：副摄只有水平 u，同列前后重叠物体会叠成一块侧影。旧做法允许一块侧影被多个顶视目标共用，标签只能随便挑一个，于是侧影上出现别的物体的类别；并且旧逻辑只按 |Δu| 配对，可能把黄物体配到红侧影上。
- 新规则（`new_eye/fusion.py::_match`）：
  1. 每块副摄侧影**最多配一个**顶视目标（一对一，不再共用、不再标 `×N`）；
  2. 两路颜色都识别出来且明显不同 → **绝不配对**（`_color_penalty >= .10` 直接跳过），所以副摄画面上的类别标签永远与顶视一致；
  3. 匹配仍按 `score = |Δu| + 颜色惩罚` 从小到大贪心分配，左右翻转两种对应关系各试一次，取配对数多/代价小者。
- `views` 三种取值：`top+side`（两路印证）、`top`（副摄未印证，面板 tail 标注“（副摄未印证）”）、`side`（副摄单独看到，标“副摄待确认”，不参与类别统计）。
- `color_mismatch` 字段保留但基本不会再出现（只可能在颜色“未知”时才配上不同物）；`need_review` 仍会合并它。
- `gui.py::draw_targets()`：副摄画面直接按融合项逐项绘制（每块侧影一个标签），删掉了按 `id(side)` 分组取 rep 的 `×N` 逻辑。

## 17. 2026-10-18 更新：副摄方向（镜像/同向）与融合诊断

- `fusion.fuse(top, side, max_dist, flip_mode=0, info=None)`：`flip_mode` 0=自动试两种、

  配对数为 0 且两路都有目标时，再增加一行 ⚠ 提示（检查方向与副摄四点顺序）。
- `latest_targets.json` 新增顶层 `fusion` 字段（即上面 info 的内容），外部程序可据此判断本次
  融合是否有效。

## 18. 2026-10-18 更新：副摄“对齐轴”+ 重复框合并 + 标签避让

### 18.1 为什么要“对齐轴”
副摄是从侧面**水平**看托盘的，它画面的水平方向只可能对应托盘的一根轴：
装在托盘短边外 → 水平方向对应托盘的 u（左右）；装在长边外 → 对应 v（前后）。
之前融合一律拿副摄 u 去和顶视 u 比，装错一边时两路坐标根本不在同一根轴上，
就会出现“明明有融合却配不对/同一物体两路不同类”。
现在 `fusion.fuse(top, side, flip_mode, axis_mode, info)`：
- `axis_mode` 0=自动（u/v × 翻转共 4 种组合都试，取配对数多、Δ 小的），
  1=强制左右(u)，2=强制前后(v)。
- 诊断里多 `axis`/`axis_name`，面板【融合】行显示`对齐轴 左右(u)（自动）`。
- 底部工具栏新增“对齐轴”下拉（自动/左右/前后），写 `config.json` 的 `side_axis`。

### 18.2 重复框合并（new_eye/auto_segment.py）
同一物体常被提示出“顶面掩膜”和“整体掩膜”两张，两者 IoU 可能只有 .2~.4，
原来的 IoU<.45/包含<.72 去重留不住 → 画面上同一物体两个框。新增 `_near()`：
两掩膜中心距 < 0.35×较小框长边、且面积比 > .25 视为同一物体，只保留较大的一个。
实测 crop_test 仍是 5 个目标，空托盘仍 0 个。

### 18.3 标签避让（new_eye/gui.py）
`_place_label()` 依次尝试框上方、框下方、再向上/下错 20px 的 9 个位置，避开已放置
的标签矩形（`self._labels`），字号 13→12；目标密集时标签不再糊成一片。

### 18.4 验证
GUI 测试（crop_test 顶视 + 合成镜像副摄）：面板【融合】= 顶视 5 / 副摄 5 → 配对 3 个

## 19. 2026-10-18 更新：视觉结果通讯（笔记本 ↔ 香橙派/单片机）

### 19.1 链路选择
| 链路 | 适用 | 说明 |
|---|---|---|
| 网线直连（推荐） | 笔记本 ↔ 香橙派 | 两端设同网段固定 IP（如 192.168.137.1 / .2），或开启 Windows 网络共享 |
| WiFi 同一路由 | 同上 | 注意现场 2.4G 干扰、IP 会变（建议路由器绑 MAC） |
| USB 串口 | 香橙派 ↔ STM32/Arduino | CDC/CH340，115200 起 |
| USB 网卡 | 无路由器时 | 笔记本插 USB 网卡，与板子直连 |

比赛规则允许笔记本通讯（`pdftext.txt:29`），所以“笔记本跑视觉 + 机器人跑运动”是合规架构。

### 19.2 协议（TCP，端口默认 5055，每行一个 JSON）
```json
{"seq":12,"ts":1730000000.123,"n":3,
 "targets":[{"id":1,"u":0.45,"v":0.38,"class_id":"1","class_name":"圆柱黄",
             "views":"top+side","area":12271}],
 "fusion":{"matched":4,"axis":"u","flip":true}}
```
- `u`/`v` 是**托盘归一化坐标**（0~1，左上为原点），机器人乘托盘实际尺寸即得抓取点；
  这也顺带解决了“像素当量未标定”的问题（只需量托盘长宽）。
- `views`：`top+side` 两路都看到、`top` 副摄未印证、`side` 副摄多出（顶视漏检）。
- 每帧约 300~800 字节，1 fps 量级，带宽完全不是问题。

### 19.3 代码（new_eye/link.py）
- `TargetServer(port)`：视觉端 TCP 服务，`start()/send(payload)/stop()`，支持多客户端，
  自动踢掉断开的连接；GUI 顶栏勾“网络推送”即启动（端口取 config `link_port`，默认 5055）。
- `TargetClient(host, port, on_frame)`：机器人端，断线 1s 自动重连。
- `control_frame(payload)`：把 `latest_targets.json` 压成上面的小帧。
- `pack_uart(payload)` / `unpack_uart(buf)`：`0xAA55 + len(2B LE) + JSON + crc16(2B LE)`，
  CRC-16/MODBUS；Pi 收到 TCP 帧后原样写串口给单片机。
- 示例：`new_eye/link_robot_example.py`（打印 + 可选串口转发 + 2s 无帧超时提示）。

### 19.4 使用步骤
1. 笔记本：GUI 顶栏勾“网络推送”→ 面板日志显示 `网络推送已开启：端口 5055，本机 IP 192.168.x.x`
2. 第一次要放行防火墙：Windows 弹窗选“允许专用网络”，或
   `netsh advfirewall firewall add rule name="new_eye" dir=in action=allow protocol=TCP localport=5055`
3. 香橙派：`python new_eye/link_robot_example.py <笔记本IP> 5055`
4. 单片机：`python new_eye/link_robot_example.py <笔记本IP> 5055 /dev/ttyUSB0 115200`

### 19.5 安全约定
- `latest_targets.json` 里 `motion_authorized` 恒为 `false`，运动使能由机器人端自己判断
  （例如：收到一帧 → 计算 → 执行，超过 1~2 s 没新帧就停车）。
- 视觉只有 0.7~1 fps，**不要用视觉做闭环**；机器人应“看一眼 → 规划 → 动到位”。


### 19.6 只能无线通讯时怎么做（笔记本 ↔ 香橙派）

三种无线方式，按现场条件选：

1. **笔记本开热点（最省事，无需路由器）** —— 设置 → 网络和 Internet → 移动热点 → 打开
   - 笔记本自动变成 `192.168.137.1`；香橙派连这个热点，IP 一般是 `192.168.137.x`
   - 热点建议开 5GHz（`netsh wlan show interfaces` 看是否支持），2.4G 现场很挤
   - 无需任何额外配置，`link.py` 的 TCP/5055 + UDP/5056 直接可用
2. **同一个路由器（最稳定）**
   - 关键：**关掉“AP 隔离/客户端隔离”**，否则两个设备互相 ping 不通
   - 路由器里给香橙派绑 MAC 固定 IP；香橙派关掉省电（`iw dev wlan0 set power_save off`），
     否则空闲几百毫秒就卡一下，延迟从 3ms 变 200ms+
3. **香橙派开热点、笔记本连** —— 反向也行，但笔记本切 WiFi 会影响本机网络，不推荐

**不用记 IP**：视觉端勾“网络推送”后，`link.py` 每 0.8s 往 UDP 5056 广播自己的 IP/端口，
机器人端 `link.discover()` 自动找到，示例脚本默认就是 `auto`：

```bash
# 香橙派上（自动发现，无线/有线都不用改）
python3 new_eye/link_robot_example.py

# 发现失败（多播被路由器拦/网段隔离）时才需要写死 IP
python3 new_eye/link_robot_example.py 192.168.137.1 5055
```

**延迟参考**：5GHz 同路由 RTT 2~10ms，2.4G 5~40ms，笔记本热点 3~15ms；
我们一帧数据 300~800 字节、1 fps，无线完全够用。真正的风险不是带宽，是丢包导致 TCP 卡顿 →
所以机器人端必须做“超时没新帧就停车”，示例里已有 2s 超时提示。

**没有 WiFi 时的兜底**：
- 蓝牙串口（RFCOMM）：香橙派 `rfcomm bind 0 <笔记本蓝牙MAC> 1`，笔记本侧用蓝牙串口，
  速率约 100~200 KB/s、延迟 20~100ms，跑 1fps JSON 够用，但配对极麻烦，只作应急；
- USB 无线数传模块（如 2.4G NRF24/433M）通常是给单片机用的，香橙派要加 USB 转接，
  带宽更小，不建议；
- 比赛现场若允许，**网线直连永远是最稳的**（`pdftext.txt:29` 允许与笔记本通讯）。

## 20. 2026-10-18 更新：X/Y 标定向导 + 转盘位置记忆

### 20.1 为什么需要标定
new_eye 给的是托盘归一化坐标 (u,v)，机器人要的是 X/Y 脉冲，两者是二维仿射：

> 不再移动后再读 u/v，不依赖回读、也不依赖人推。下面 1~5 步是它最早的手动分步版本，仍可用作

### 20.5 手推标定模式（v3，2026-10-18 晚，取代电机带动为默认）

**为什么改**：电机带动模式要“走 N 脉冲 → 等它到位 → 再识别”，而“到位”只能靠 `_wait_ms`
估算（固件 acc 是加速档位、不是 rev/s²，且没有 X/Y 回读可以轮询），现场很难用。
用户反馈“太不好用了这模式”，改成：电机不使能 → 人用手推 → 读编码器回读定位。

**原理**：
- 编码器回读 65536 counts/圈（`host_gui.py` `COUNTS_PER_REV`），运动 3200 脉冲/圈，
  故 1 脉冲 = 20.48 counts；`calib_wizard.counts_to_pulses()`、`wrap_delta()` 负责换算与回绕；
- 每个采样点同时存 `u,v`（视觉）和 `counts_x,counts_y`（回读），相邻点差分得到 `px,py`，
  多点的 `(px,py) ↔ (u,v)` 用同一套最小二乘解仿射（`tray_calib.solve`）；
- 3 点即可，建议 4~5 点（X 单独、Y 单独、斜着各来一次），分散开避免奇异。

**限制**：单圈编码器只测最短路径，两点间真实位移 ≥ 半圈时方向会判错。
`hand_points(max_delta_ratio=0.45)` 会把超过 0.45 圈的跳变打上提示，手册要求单次推动 < 1/3 圈。

**界面**（`ghr/10.15/上位机/calib_dialog.py`，820×700，顶部单选模式）：
| 控件 | 作用 |
| --- | --- |
| ① 取消 X/Y 使能（可手推） | `stop_all` + `motor_enable 0`，之后可手推 |
| ② 记录当前位置（视觉 + 回读） | 读一次视觉 u/v + 查一次 X/Y 编码器，存一个采样点 |
| 撤销上一个点 / 清空采样 | 修正误记 |
| ③ 求解并保存标定文件 | `calib_wizard.solve_hand()` → 写 `new_eye/tray_calib.json`（自动备份旧文件） |
| 恢复 X/Y 使能 | 标定完必须点，否则电机没力矩 |
| 回读：X=… Y=… counts | 判断回读是否通 |
| 采样列表 | 每点 u/v/counts + 相邻点 Δ脉冲 |

**代码**：`calib_wizard.py` 新增 `COUNTS_PER_REV/PULSES_PER_REV/counts_to_pulses/wrap_delta/
hand_points/solve_hand`；`solve(..., labels=('第 2 点','第 3 点'))` 让手推模式报错文案不串成
“X/Y 点”；`report(result, span)` 的“走 N 脉冲 ≈”用实际采样量程当 span。对话框冒烟测试：
3 个手推点（0/6553/6553 counts）解出 `a=d=3199.7 脉冲/u`、残差 1e-12 量级。
测试：`ghr/10.15/上位机/tests/test_calib_wizard.py` 14 个用例（含“超过半圈”与“点数不足”）。
手册：`new_eye/标定操作手册.md` 第 3~8 步已改为手推流程，电机带动降为“备选”。

> 回读前提：固件 hello 的 `readback` 名单要含 X(4)/Y(5)（`readback_mask` 默认 15 已含），
> 且 X/Y 的 TXD 要接到 PA3 并联总线；否则向导会提示“该轴不在回读名单/查不到回读”。

## 21. 2026-10-18 更新：标定向导 v4（电机走 + 等画面停，取代手推为默认）

### 21.1 为什么放弃“手推”
用户实测反馈（“点了取消使能还是推不动”）。查固件后确认不是向导 bug：
- `ghr/10.15/Drive/Include/control_inline.h` 的 `control_apply_enable()` 失能时调用
  `Stepper_EnableAt(addr, 0)`，再 `rpm=0 / mode=STOP`；
- `stepper_inline.h` 的 `Stepper_EnableAt()` 是给驱动器**发一帧使能/失能命令**
  （ZDT/Emm42 类 6 字节帧，`build_enable()`），不是拉本地使能引脚；
- 现场驱动器多为**闭环步进**，即使收到失能帧，驱动器内部仍可能保持位置环；
- 更关键：X/Y 若是滚珠丝杠/蜗轮蜗杆等**自锁传动**，取消使能后也推不动（这是机械属性）。
- 另外 4 路驱动器 TXD 并联回读在硬件上未验证（`ghr/10.15/交接文档-20261016.md` 记为方案 A 只接 1 路），
  所以“手推 + 回读”这条路在本机大概率走不通。

### 21.2 新方案：电机走固定脉冲，等“画面里物块不动了”再读
- 运动：`motor_pos` 走 N 脉冲（可负，负=dir 1），继电器/固件自己保证走完；
- 停稳判定：轮询 `new_eye/runtime/latest_targets.json`，要求
  ① 出现比移动前更新的帧（`vision_ts > prev_ts`）；② **连续两帧**同一目标的
  `|Δu| + |Δv| ≤ SETTLE_TOL`（0.0025）。满足即认为平台停了；
- 记录：此刻 u/v + **指令脉冲** (px,py)，不再需要编码器回读、不再需要估算时间；
- 采集点：基准 (0,0) → X 走 N → 停稳记录 (N,0) → X 回位 → Y 走 N → 停稳记录 (0,N) → Y 回位 → 求解；
- 超时兜底：30 s 内没等到“新帧+停稳”就报错（提示开实时分割 / 去点两次“单次识别”）。

## 23. 2026-10-18 更新：标定“简化求解”（治“矩阵奇异/共线”）

- 现场用“通用 3 点”常失败：`变换矩阵接近奇异，标定点可能共线`——多半是两次移动都沿同一方向
  （只走 X 没走 Y），或脉冲没变化（软位置没记上）。
- `calib_wizard.py` 新增：
  - `check_points()` 补两类诊断：① 所有点脉冲完全相同 → 提示“没记录到移动”；
    ② 只有一个轴变化过 → 提示“再走一段另一个轴”；
  - `solve_ortho(points, ...)`：只假设 **X→u、Y→v**（b=c=0），用“Δpx/Δu”和“Δpy/Δv”直接定标，
    从数学上不可能奇异；返回 `mode='ortho'` 与 `coupling`（X 走时 Δv/Δu、Y 走时 Δu/Δv）。
  - `report()` 对 ortho 结果加标题行与“旋转/耦合检查”：|比值|>0.30 时 ⚠ 提示两轴不垂直/相机装歪。
- `calib_dialog.py`：新增按钮 **「简化求解（只走 X/Y）」**（`on_solve_ortho`）；
  「③ 求解并保存」失败且是共线/奇异时弹窗询问“改用简化法吗”，同意即 `solve_ortho`；
  结果输出抽成 `_show_result()`；界面提示文字写明“只走两次即可”。
  窗口 940×740。
- 测试：`tests/test_calib_wizard.py` 新增 `TestOrthoSolve` 5 例（恢复比例、单轴拒绝、无 u/v 变化拒绝、

## 22. 2026-10-18 更新：标定向导 v5（手动走轴 + 视觉记录，最终采用）

### 22.1 为什么 v4 也不好用
- v4 让向导自己发 `motor_pos`，再用“连续两帧 u/v 差 < 0.0025”判停稳。
- 实测：`标定失败：标定点不合格（Δu=-0.001 Δv=-0.000）`——电机没使能/没动、或
  实时分割帧率太低（0.5~1 fps）、判稳窗口里拿到的其实是同一帧，于是“看起来没动”。
- 排查还发现固件一个真问题：`control_inline.h` 里 `motor_pos` 的 `mode` 参数被忽略，
  始终走 `Stepper_MoveRelativeAt2(..., absolute=0)`，即 **abs 实际是相对**；
  `Stepper_MoveAbsoluteAt()` 定义了但没被调用（已单独告知用户，修法 A/B 待选）。

### 22.2 v5 流程（用户指定）
1. new_eye 点一次「单次识别」，目标 u/v 写入 `new_eye/runtime/latest_targets.json`；
2. 上位机标定向导点「① 读取视觉 u/v」，再点「② 记录坐标」→ 存 (u, v, 当前软位置 X/Y)；
3. 用户用**单轴页**（X(4)/Y(5) 面板「▶ 相对走」）手动把平台走到下一个位置；
4. 再点「单次识别」→「① 读取」「② 记录」→ 第 2 个点；
5. 「读取现在走过的脉冲」可核对当前软位置与相对上一点的 ΔX/ΔY；
6. 「一键回 0 脉冲点（X/Y）」按软位置把轴开回 0 基准点；重复到 3~5 个点；
7. 「③ 求解并保存标定文件」。

关键点：脉冲来自上位机的**软位置记账**（`HostClient.motion_hook` → `App.soft_pos`，
相对运动累加；连续/绝对模式置 `pos_known=False`），不依赖编码器回读，也不需要改固件。
