## 1. 回读与 motor_query（今天的第一个发现）

### 1.1 实测事实

| 测试 | 结果 |
|---|---|
| `motor_query`（主动查询四轴位置/速度） | **20 次 0 成功**：8/8 E04、6/6 E04、5/6 E04 + 1 次 E09 |
| E04 往返耗时 | 62 / 79 / 93 ms（轴 3 / 轴 1 / 轴 4）→ 比 `query_timeout_ms`=100 ms 还短 |
| `tele_on` 遥测 | 3 秒 75 帧，四轴都有真实 counts：Z=2,757,257、托盘=7、X=−31,111、Y=446,243 |
| 遥测新鲜度 | `age_ms` 能回到 1–67 ms → 后台轮询确实在成功刷新 |
| 关掉遥测后再查询 | 8/8 仍 E04，`last_counts` 空 |

**换算**：65536 counts = 1 圈，32 位多圈累计 → Z 的 2,757,257 counts ≈ 42 圈，Y 446,243 ≈ 6.8 圈。

### 1.2 结论

1. **物理回读链路没问题**——以前写在 `02-资料库/02-硬件/README.md:23` 和 `01-交付包/VERSION.md:28` 的"PA3 未接线 → E04"是**错的**，需要改；
2. 坏的是**"PC 发查询 → 固件转发 → 回包配对"这条状态机**，而且不是"等满 100 ms 才超时"，是**提前判过期**；
3. 你截图里四轴的"回读：…脉冲/…°，0.1s 前"**是真的**，数据来自遥测（`host_gui.py:326-340 update_telemetry` → `:182` 标签由 `refresh_readback()` 渲染）。

### 1.3 主假设（还没钉死）

`sent_ms` 与 `stamp_ms` 不同源：

- 查询命令在 `host_cmd_motor_query()` 里现取一次 `Stepper_Millis()` 当 `sent_ms`（`host_protocol_inline.h:1393`）；
- 而 `host_query_has_fresh_data()`（`:680-687`）要求 `stamp_ms >= sent_ms`，`stamp_ms` 来自任务循环开头那次 `now`（`:1836`）；
- 同一次主循环里 `now` 比 `sent_ms` 旧 → 条件恒假 → 回包被当旧包丢掉 → 最终 E04。

但 62–93 ms 的耗时说明**还有第二处状态机问题**，光靠读代码钉不死。

### 1.4 两条修法（明天二选一）

|---|---|---|---|
| **A 先绕开** | 上位机"查位置/查速度"改用遥测缓存（`last_counts` 已有），`motor_query` 按钮标记"暂不可用" | 0 改固件、0 烧录，几分钟 | **今天就能用** |

## 2. 用遥测闭环（能不能靠 counts 做出"到位"判断）

### 2.1 能做的 4 件事

1. **到点判定**：不等时间，等 `|counts − target| ≤ tol`；
2. **丢步/堵转检测**：发 N 脉冲，比较 counts 实际变化，偏差 >3% 就停、报警；
3. **两段式逼近**：先快走 90–95%，再按剩余 counts 慢速补最后一段；
4. **往返漂移检测与补偿**：每次回到 P0 与上电基准比对，超阈值补一小段。

### 2.2 做不到的 3 件事

| 限制 | 原因 | 对策 |
|---|---|---|
| 实时伺服 | 每轴新数据 ≈ 4×`telemetry_ms`（默认 200 → 400 ms） | 只做"到点确认"，不做连续伺服 |
| 机械背隙 | counts 是电机端编码器，看不到丝杠反向间隙 | **单向逼近**：总从同一方向趋近目标 |
| 掉电绝对位置 | 驱动器计数断电行为未实测 | 上电先全轴读一次记基准，不假设 0 |

### 2.3 闭环结构（三段式）

```
目标 3200 脉冲
 ①快走 3000 脉冲（93%）
 ②等 ≥1 个遥测周期（400 ms），读实际 counts
 ③补差：剩余 = 3200 − 实际；|剩余| < 死区(100–300 counts) 就算到
   补两次还差 → 报警（卡住/皮带松）
```

**死区取 100–300 counts（0.5–1.6°）**：机械误差远大于编码器分辨率，设太小会抖动。

### 2.4 明天要做的 4 个标定实验（需要动电机，等你点头）

| 实验 | 做法 | 产出 |
|---|---|---|
| A 比例 | X 轴走 3200 脉冲，读前后 counts 差 | `counts/脉冲` 实际系数 |
| B 重复性 | 同一动作重复 5 次 | 误差分布 → 死区取值 |
| C 反向间隙 | 正走一段再反走同样量 | 背隙大小 → 是否必须单向逼近 |
| D 遥测延迟 | 发指令后每 100 ms 读一次 | 实际刷新周期 → "等几拍" |

一次约 1 分钟动作（60 RPM、每次 1 圈）。跑完写成 `02-资料库/05-调研报告/遥测闭环标定.md`。

## 3. 从初始位置开始的抓取流程（今天的主线）

### 3.1 你要的流程（原话）

> "上电是初始位置，然后不动，开始抓取后走的路线自动加上一段，然后抓取后原路返回，初始位置就是释放物体的位置，然后再进行第二次抓取"

```
上电 → P0（不动）
  │ 按下「开始」
  ▼
P0 ──[通道段 C 正序]──► P1（取料区）── 拍图→对准→Z下→夹135→Z上
                          │
P0 ◄──[通道段 C 倒序取反]──┘
  │
  └─ 夹爪 180 松开（在 P0 释放）→ 第二件：P0 → C → 抓 → C⁻¹ → P0 → 松 …
```

### 3.2 关键区别（为什么不是直接用 `journey.py`）

| | `journey.py`（现有的"回上电初始位"） | 你要的往返模式 |
|---|---|---|
| 记录范围 | 上电后**所有**移动（含抓取、托盘转位） | **只记通道段 C** |
| 返回时机 | 手动点按钮，一般整轮结束回一次 | **每件抓完自动返回** |
| 触发 | 手动 | 「开始」后自动循环 |

结论：**新增独立的通道段数据 + 往返状态机**，比改 `journey` 干净得多。

### 3.3 实现清单（约半天）

1. `corridor.json`：一组相对脉冲段 `{axis, dir, rpm, acc, pulses}`，示教复用现有「开始示教」录制逻辑；
2. 往返执行器 `corridor.py`：
   - 正序 = 原序执行；倒序 = `reversed()` 且每段 `dir ^= 1`；
   - 每段：`motor_enable` → `motor_pos rel` → 按 `pulses/rpm` 等时 → 200 ms 稳定；
3. **抓取宏**：把「拍图 → 对准 → Z 下 → 夹 135 → Z 上」串成一个函数（现在都是分步按钮）；
4. **释放宏**（在 P0）：Z 下（若需要）→ 夹爪 180 → 稳定 → Z 上 → 夹爪回 150；
5. **每件 counts 校验**：回 P0 后与上电基准比对，偏差 >500 counts（≈2.7°）报警/微调。

### 3.4 状态机

```
IDLE → OUT(C正序) → PICK(拍图/对准/抓) → BACK(C⁻¹) → RELEASE(松爪) → 计数+1
     → 还有货? OUT : IDLE
任意状态超时/异常 → FAULT（停车 + 屏提示 + 可恢复点）
```

### 3.5 你还需要确认 2 件事

1. **P0 释放到哪里**？
   - (a) P0 就是六盒转盘（转回去放进对应盒）；
   - (b) P0 有固定滑槽/料框，直接丢；
   - (c) P0 是空的，先走到某处再放。
2. **P0 释放时有无干涉**（线缆/立柱/夹具）？夹爪在 P0 张开会不会碰东西。

### 3.6 风险

| 风险 | 数据/对策 |
|---|---|
| 累积误差叠加 | 12 次往返，开环可能漂几 mm；靠每件 counts 校验 + 必要时加光电 |
| 节拍变长 | 通道去 2 s + 抓 4 s + 回 2 s + 释放 1 s + 拍照对准 2 s ≈ 12 s（15 s 内但余量小） |
| 通道越长越慢 | 示教时在保证不撞的前提下尽量少段（能 3 段不要 5 段） |
