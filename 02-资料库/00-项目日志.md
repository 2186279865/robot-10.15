## 2026-10-21 · final/run.bat 双击打不开："'m' 不是内部或外部命令"

**背景**
用户报"final 文件夹里的 run.bat 打不开了"。这类问题在现场最要命：明明代码是好的，双击就废。

**方案取舍**
- 先怀疑解释器路径（`final/.venv` 不存在）→ 用 `Qwen/.venv` 手动跑 `main.py --selftest`，8 页全过，说明**逻辑没问题**。
- 再看文件字节：539 B、无 BOM、CRLF=0、LF=17，中文是 UTF-8 多字节。结论：cmd.exe 按系统 ANSI 码页逐字节解析批处理，UTF-8 中文 + LF-only 会把行边界切错。
- 修法三选一：①只改换行（CRLF）②改 GBK+CRLF ③**纯 ASCII + CRLF**。选 ③：跨语言环境最稳，代价是注释和提示只能写英文。

**做了什么**
- 重写 `run.bat` / `setup.bat` 为纯 ASCII + CRLF（逻辑一字未改），并在注释里写明"为什么必须 ASCII+CRLF"。
- 全仓扫了一遍 `.bat/.cmd`：其余本来就纯 ASCII，Keil 自带的 `keilkilll.bat` 带 CRLF 不动。
- `使用说明.md` 故障排查表加了一行：见到 `'m' is not recognized` 就是这个坑。

**验证**
`cmd /c "run.bat --selftest"` 8/8 页；`setup.bat` 在"PATH 里没有 python"时能正确报错退出；真双击截图留证。

**遗留 / 风险**
这是**通用陷阱**：以后任何 `.bat` 被编辑器另存成 UTF-8 就复发。后来把这条写进了交付包的 `CHECK.py`（检查非 ASCII 字节 + CRLF）。

**放弃的念头**
- 想用 PowerShell 脚本代替 .bat → 放弃：现场双击体验不如 .bat，且 PowerShell 执行策略又是一层坑。

## 2026-10-21 · "final 能不能跑在香橙派 4 Pro 12G 上"

**背景**
想把整套系统塞进一块 55 美元的香橙派。要先回答：算力够不够，尤其是视觉。

**方案取舍 / 实测**
- 直接在笔记本 CPU 上跑 SAM-B 计时（700×700、1 点 prompt）：加载 0.57 s，**单次分割 6.2–6.7 s**（8 线程 Ryzen 9 8940HX）。
- 按 A733（2×A76 + 6×A55，无 CUDA）保守估 4 倍 → **20–30 s/帧**。结论：SAM 在派上不可用；而控制端（tkinter + 串口）在派上完全跑得动。

**做了什么 / 结论**
- 给出三条路线：A 派只当控制端（`--no-vision`）；B 全派化（必须换 YOLO11n-seg 之类轻模型，SAM 换掉）；C 换 RK3588 + RKNN。
- 关键判断：**12 GB 内存不是瓶颈，算力才是**；而且 RKNN 工具链冷门、散热、USB 带宽都要另外折腾。

**验证**
只用真实计时和公开规格推算，没有真机跑过（板子还没到）。这条后来被证实方向正确：真机到手后，最终架构是"派采集 + 笔记本识别"。

**放弃的念头**
- 一开始想"干脆重写一个轻量视觉" → 放弃：分割质量直接决定抓取成功率，SAM 的泛化是这套系统的立身之本，不能为了板子换模型。

## 2026-10-22 · 架构定调：派采集、笔记本识别、串口桥透传

**背景**
用户提出真实链路："香橙派连 STM32，相机连香橙派，派把画面无线传给笔记本，笔记本识别，再下发运动指令抓取"。

**方案取舍**
四个方案对比：
1. **相机上派 + 串口桥**（拉模式拉静帧，笔记本识别）；
2. 实时视频流（RTSP/H.264），派端硬编码；
3. 控制下沉到派（笔记本只看）；
4. 全派化（换轻模型）。

量化后选 ①：SAM 在笔记本上 0.8–1 s/帧占绝对主导，而一张 720p JPEG 上行只要 10–40 ms、带宽 <1 Mbps → **根本不需要视频流**。方案 2 要折腾全志编码器插件；方案 3 要把 5000 行 tkinter 搬到派；方案 4 要换模型。①还有一个决定性优点：**协议零改动、固件零改动、默认行为不变**（`--pi` 不传时完全等价于原来）。

**做了什么**
- 定了三条通道：TCP 5057 图传（拉模式：笔记本发 9 字节请求，派回 24 字节头 + JPEG）、TCP 5058 串口桥（字节透传）、UDP 5056 发现。
- 定义了三层安全网：界面急停 → 派端 1.5 s 无字节发停车帧 → 固件 3 s 心跳锁存。
- 写了 `10.21/` 自包含包（后来重排成 `01-交付包/`）：派端 `pi_agent.py`、笔记本端 `RemoteCamera`/`SocketLink`/`camera_factory`。

**验证**
假派 + 假串口自测全绿；真机（香橙派）上：图传建连 10–51 ms，取一帧 1280×720 137–376 ms，串口桥 5–38 ms。

**遗留 / 风险**
- WiFi 双路 1920×1080 需要 4–7 MB/s，实际用 1280×720 更稳。
- 现场若 AP 隔离，UDP 发现收不到 → 靠"记住上次 IP"兜底。

**放弃的念头**
- 想过让派端推流（UDP 分片）→ 放弃：丢帧要重传逻辑，而"按需拉一帧"天然没有积压问题。

## 2026-10-23 · 接近段示教：从"记不住"到"三种点动都能记"

**背景**
用户要把"上电位置 → 抓取位置"这段路录下来，抓取前自动重放，避免每次手动点。第一版做出来后用户反馈：**"记录不住"**。

**根因**
第一版钩子只认 `motor_pos` 且 `mode=="rel"`。但界面上有三种点动方式：
- 「相对走」→ `motor_pos rel` ✅ 能记；
- 「绝对走到此」→ `motor_pos abs` ❌ 分支提前 return；
- 「常用走」→ `motor_speed` ❌ 完全不记。

而且没有任何可见反馈，用户不知道自己录上了没有。

**关键事实（很重要）**
固件把"绝对位置"也**按相对执行**（`control_apply_position(..., absolute=0)`）。所以 abs 点动实际走的是"目标那么多个脉冲"，不是"走到绝对位置"。这直接决定了记录逻辑：abs 也按 `(方向, 脉冲数)` 记账，而不是算目标差。

**做了什么**
- 三种点动全部纳入：rel 直接记；abs 当 rel 记（并 note 提醒"固件按相对执行"）；speed 记 `(起始时间, 方向, 转速, 加速度)`，等 `motor_stop` 或 `stop_all` 到了才按"转速 × 时间"结算。
- 每记一段就 `note("已记录第 N 段：X +3200 脉冲")`，状态行实时显示段数与净脉冲。
- 重放：先 `stop_clear`（断线后固件会锁存停止），逐段 `motor_enable + motor_pos rel`，跑完自动衔接动作序列。

**验证**
单测 22 个；冒烟 16 项（含"绝对走到此记成一段""常用走停下结算成一段"）；真机待用户验证。

**遗留 / 风险**
- 速度模式那段是**估算**，误差大（0.4 s × 60 RPM ≈ 1280 脉冲，实测 1500）。已建议示教优先用相对走/绝对走到此。
- 开环无回读，重复精度靠机械；跑偏了要重新示教。

**放弃的念头**
- 想过"录制时改写点动按钮，只允许相对走" → 放弃：限制了用户操作习惯，且 abs 本身有价值。

## 2026-10-23 · 删掉「一键回0 / 开机回基准」，改成「回上电初始位」

**背景**
用户明确说"删掉截图里的两个功能"（一键回0、开机回基准），因为实际用不上、还占顶栏；同时要一个新功能："从上电开始记录所有移动，一键原路返回"。

**为什么原来的回零不好用**
- 固件没有真正的"机械原点"，所谓"回 0"只是把**软位置**归零，不是回到某个物理位置；
- 托盘"位置清零"后仍需人工对准 1 号位，容易误以为已经校准；
- 有了"记录 + 倒放"，"回初始位"这件事才真的可执行。

**做了什么**
- 删除：顶栏两个按钮、视觉页两个按钮、X/Y 标定页与标定对话框里的回零按钮、`home_route.py` 模块/状态文件/测试、生成序列时的"还没建立基准"拦截弹窗。保留「位置清零」（只归零不运动）。
- 新增 `journey.py`：记录**四轴**（含托盘）每一次移动（命令发出即记账），最多 2000 段；「原路返回初始位」= 倒序 + 方向取反重放；返回成功后清空记录（避免再点一次往反方向走）；固件重启（boot id 变化）自动清零。

**验证**
单测 12 个（journey）+ 全量 164；冒烟 11 项（记录 3 段含托盘 → 速度模式补记 → 返回严格倒序取反 → 每段先使能 → 成功后清空 → 急停清队列）。

**遗留 / 风险**
- 开环重放有累积误差；返回后要目视确认真的回到原位。
- 记录是"本次上电以来"，固件一重启就清空。

**放弃的念头**
