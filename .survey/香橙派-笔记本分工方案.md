# 香橙派 4 Pro(12G) + 笔记本 分工抓取方案（v1 设计稿）

> 目标架构（用户口述）：**香橙派接 STM32、摄像头接香橙派、派把画面无线传给笔记本、笔记本识别、再下发运动指令抓取**。
> 本文给出端到端流程、四个可落地方案、推荐路线与一期落地细节。
> 硬件前提：Orange Pi 4 Pro / 全志 A733（2×A76 + 6×A55，3 TOPS NPU，无 CUDA，WLAN 6），12GB 内存。

---

## 0. 一句话结论

**推荐"方案 1：相机上派 + 串口桥"做一期（2–3 天可联调）**：
派只做两件事——按需抓图（JPEG 回传）和把笔记本发来的协议行**逐字节透传**给 STM32；
视觉（SAM/融合/分类/标定/规划）与全部 GUI 仍留在笔记本。
这套改动只碰三个文件、不动协议、不动固件，且天然保留了现有的"3 秒失联自动停车"安全网。
二期若时间允许，再上"方案 3：控制下沉派"或"方案 4：全派化"。

## 1. 三种职责切分（先定"谁做什么"，方案才有意义）

任何方案都是下面三层职责的切分方式不同：

| 层 | 职责 | 候选承载 |
|---|---|---|
| L1 执行层 | EMM V5 四轴 + 舵机 + 按键 | STM32F407（已定型，不动） |
| L2 控制层 | 19 条上位机命令、动作序列、视觉规划→脉冲、状态机、急停 | 笔记本（现状）/ 派 |
| L3 感知层 | 双相机采集、单应、SAM 分割、融合、分类、u/v 输出 | 笔记本 GPU（现状）/ 派（需换模型） |

用户描述的架构 = **L1 在 STM32、L3 在笔记本、L2 在笔记本**，派是新增的"摄像头 + 串口 + 无线路由"三合一网关。
因此本方案的本质问题是：**如何把"相机"和"串口"这两个本地资源网络化，同时不破坏现有 5000 行上位机与固件协议。**

## 2. 端到端流程（以抓取 1 件为例）

```
 [USB cam Top]  [USB cam Side]
        │              │
        └──────┬───────┘
         ┌─────▼──────────────────────────────┐
         │ 香橙派 4 Pro (Ubuntu/Debian, V4L2) │
         │  camera_agent  ── JPEG(质量75) ──┐ │
         │  serial_bridge ◄── /dev/ttyACM0 ─┼─┼─ USB ──► STM32F407
         └───────────┬──────────────────────┘ │
                     │ WiFi6 (笔记本热点 / 5G 路由器)
         ┌───────────▼──────────────────────┐
         │ 笔记本：final/main.py (8 页 GUI) │
         │  RemoteCamera → 单应 → SAM → 融合 │
         │  → 分类 → tray_calib → 脉冲规划   │
         │  → SocketLink（TCP 5058 串口桥）  │
         └──────────────────────────────────┘
```

单件时序（预算：赛项要求 15 s 内无动作即本件结束）：

| # | 步骤 | 承载 | 预估耗时 | 备注 |
|---|---|---|---|---|
| 1 | 触发"单次识别"/实时预览取最新帧 | 笔记本→派 | 请求 RTT 5–15 ms | 拉模式，不排队 |
| 2 | 双相机采集 + JPEG 编码 | 派 A76 | 720p 12–25 ms / 1080p 25–45 ms | libjpeg-turbo |
| 3 | 上行传输 | WiFi6 | 720p 110 KB / 1080p 220 KB → 10–40 ms | TCP，长度前缀分帧 |
| 4 | 解码 + 单应 + 前景候选 | 笔记本 | 10–20 ms | 现有代码 |
| 5 | SAM-B 分割（GPU） | 笔记本 RTX 5060 | **800–1000 ms** | 现状实测 0.98 fps |
| 6 | 双摄融合 + 规则分类 + 标定→脉冲 | 笔记本 | 20–50 ms | 现有代码 |
| 7 | 规划 + 下发命令（`$...#...*CS\n`） | 笔记本→派→STM32 | 命令 RTT 8–25 ms | 串口桥 |
| 8 | 固件解析 → 驱动器起转 | STM32 | 10–30 ms | 帧间 ≥10 ms |
| 9 | Z 下降/夹紧/上升/托盘转位 | 机构 | **1.5–6 s** | 节拍主导项 |

**结论：感知链 ≈ 1.0–1.2 s，节拍 5–9 s/件，无线带来的额外时延（<60 ms）相对 SAM 的 800 ms 可忽略。**
这正是"图传不必做实时视频流"的量化依据。

## 3. 四个方案

### 方案 1：相机上派 + 串口桥（推荐一期）

- **拓扑**：派 = 图传服务（TCP 5057 按需抓图）+ 串口桥（TCP 5058 全双工字节透传）；笔记本 = 现有 final/main.py，仅替换"相机对象"和"链路对象"。
- **数据量**：每件 2–4 张 720p JPEG ≈ 0.2–0.5 MB；12 件/轮 ≈ 3–6 MB。带宽压力几乎为零。
- **改动清单**：

| 文件 | 改动 | 规模 |
|---|---|---|
| `new_eye/pi/camera_agent.py`（新） | V4L2 抓图、JPEG 编码、TCP 拉模式服务、可选 MJPEG 预览 5059 | ~200 行 |
| `new_eye/pi/serial_bridge.py`（新） | TCP 5058 ↔ `/dev/ttyACM0` 双向透传、重连、本地看门狗（1.5 s 无命令发 FE 停车帧） | ~150 行 |
| `new_eye/pi/systemd/*.service`（新） | 两个服务开机自启（参考 `new_eye/无线组网联调.md:128` 的写法） | ~30 行 |
| `new_eye/camera.py` | 加 `RemoteCamera`（与 `Camera` 同接口 `read()/release()`），按 config 选择本地/远程 | +60 行 |
| `new_eye/config.json` | 加 `camera_source: {"mode":"remote","host":"192.168.137.2","port":5057}` | +6 行 |
| `ghr/10.15/上位机/serial_link.py` | 加 `SocketLink`（open/close/write/read/connected/describe 六方法），`open_best_link()` 识别 `tcp://host:5058` | +70 行 |
| `ghr/10.15/上位机/host_gui.py` | 端口下拉加"网络链路(tcp://…)"输入项 | +20 行 |
| `final/main.py` | `--pi 192.168.137.2` 参数，串起来 | +15 行 |

- **优点**：复用 100% 视觉与控制逻辑；协议零改动；固件零改动；保留现有 8 页 GUI 与屏（笔记本 HDMI）；工程量最小、可回退（改回 COM 端口即可）。
- **缺点**：多两跳（图传/控制），对 WiFi 质量敏感；两处常驻服务需 systemd 守护。
- **工期**：2–3 天（含联调与压测）。

### 方案 2：实时视频流（H.264/RTSP）+ 串口桥

- 派用硬件编码器（A733 支持 4K H.265 编码）出 RTSP/RTP，笔记本 `cv2.VideoCapture("rtsp://…")` 取最新帧。
- **带宽**：720p/15 硬件编码 ≈ 1.5–3 Mbps/路，远低于 JPEG 连续流；时延 100–200 ms。
- **优点**：可做实时预览、视觉伺服（边动边看）、调标定直观。
- **缺点**：全志编码走 cedarc/mpp 插件，Orange Pi 官方镜像是否自带 gstreamer 插件需实测；丢包花屏、首帧慢；调试成本高。
- **工期**：3–5 天（一半时间在折腾编码器）。
- **适用**：想上"接近跟随/视觉伺服"（参考 `xrw/例35` 的 XY 跟随思路）时再考虑；单纯抓取不需要。

### 方案 3：控制下沉派（笔记本只做"算力外挂"）

- 派：相机 + **上位机（headless）+ 规划/序列 + 屏显示**；笔记本：只识别，把目标 JSON 发回派。
- 下行已是现成协议：`new_eye/link.py` 的 **TCP 5055 NDJSON**（`TargetServer`/`TargetClient`，UDP 5056 自动发现），`new_eye/link_robot_example.py` 就是"机器人端接收示例"骨架，可直接改成派端程序。
- **优点**：下行每帧几百字节，WiFi 抖动影响最小；断网可本地降级（用上一条目标/直接停车）；屏与一键启动天然在机器人侧，最贴合赛项"自主"语义。
- **缺点**：上位机 tkinter 要跑在派上（需 X 或 Wayland，字体/DPI 要调，或改成无界面 + 独立屏程序）；`tray_calib.json` 等标定产物要在派侧维护；工作量最大的是"把 5000 行上位机搬过去并验证"。
- **工期**：4–6 天。

### 方案 4：全派化（视觉也搬过去）

- 派上跑 YOLO11n-seg / FastSAM（已实测 SAM-B 在 A733 约慢 4 倍 → 单帧 20–30 s，**不可用**），笔记本退化为可选监督屏。
- **优点**：完全自主，无线只传状态；赛项合规最稳（不怕"笔记本算机器人一部分"的争议）。
- **缺点**：要写 YOLO 后端（`AutoSegmenter.segment()` 的输出契约见 `final/new_eye/auto_segment.py:197-200`，复现 dict 即可）+ 精度复验 + 标定重做；NPU 工具链冷门。
- **工期**：1–2 周。

### 方案 0（对照 / 降级路径）：相机留笔记本，派只做串口桥

不符合你的目标（相机要在派上），但联调期很实用：先验证"派↔STM32 串口桥"这一段，再接管相机，出问题可两段分开定位。

## 5. 方案 1 落地细节

### 5.1 网络与地址

- 首选：**5 GHz 独立路由器/AP**（Pi 与笔记本都当 STA），静态 DHCP 绑定：笔记本 `192.168.137.1`、派 `192.168.137.2`。
- 备选：笔记本开热点（现有 `new_eye/无线组网联调.md` 就按 192.168.137.x 写的）；Windows 热点默认 2.4 GHz 时把图降到 720p。
- 发现：沿用 `new_eye/link.py:29-30`（UDP 5056 广播 `NEWEYE1`），派端 beacon 指向自己的图传端口；找不到就用静态 IP。
- 端口规划：`5055` 目标 JSON（现有）、`5056` 发现（现有）、`5057` 图传（新）、`5058` 串口桥（新）、`5059` MJPEG 预览（新，可选）。
- **图传与控制必须分开两个 TCP 连接**，避免大帧阻塞串口回包（避免队头阻塞）。

### 5.2 三个通道的协议

**(a) 图传通道（TCP 5057，笔记本拉、派回）** —— 长度前缀二进制，简单到不用库：

```
请求  : b'RQ' + u16 cam_id + u16 w + u16 h + u8 q                    (9 B)
响应  : b'IM' + u16 cam_id + u16 w + u16 h + u32 seq + u64 ts_us
        + u32 jpeg_len + jpeg_bytes                                  (23 B + N)
错误  : b'ER' + u16 code + u16 len + msg
```
- 拉模式（谁要谁请求）→ 永不积压旧帧；`seq` 单调递增，笔记本丢弃 `>1 s` 的旧帧。
- 相机未就绪：返回 `ER`，笔记本据此**不动作**（`motion_authorized` 继续为 false）。

**(b) 串口桥（TCP 5058，全双工字节流）**

- 笔记本 → 派：就是现有 `$...#12,ok,...*CS\n` 原始字节，**一个字节都不改**（`protocol.py` 的组帧逻辑原样用）。
- 派 → 笔记本：`/dev/ttyACM0` 读到的原始字节原样回传（含 `#` 回包、`$` 事件、E0x 错误）。
- 桥不做任何解析 → 未来固件加命令不用改派端。
- **本地看门狗**（派侧，独立于笔记本）：`1.5 s` 没收到笔记本任何字节 → 直接向串口写四帧停车帧
  `01 FE 98 00 6B` / `03 FE 98 00 6B` / `04 FE 98 00 6B` / `05 FE 98 00 6B`。
  这是双保险：固件自己还有"3 秒失联只停车不关使能"（`host_protocol_inline.h` 心跳逻辑）。

**(c) 状态/心跳（复用 TCP 5055 NDJSON）**

- 笔记本每秒一帧 `{"t":"hb","seq":N,"ts":…,"fps":…,"vision":"ok|degraded"}`；
- 派回 `{"t":"hb_ack",…}` + 串口/相机健康度；用于 GUI 显示链路质量与自动降级。

### 5.3 派端两个服务（伪代码）

```python
# camera_agent.py
cap = {0: cv2.VideoCapture(0, cv2.CAP_V4L2), 1: cv2.VideoCapture(2, cv2.CAP_V4L2)}
for cam in cap.values():
    cam.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*'MJPG'))
    cam.set(cv2.CAP_PROP_FRAME_WIDTH, 1280); cam.set(cv2.CAP_PROP_FRAME_HEIGHT, 720)
# 服务循环：recv 9 字节 → 读一帧 → cv2.imencode('.jpg', q) → 打包回写
# 抓图失败/相机拔掉 → 返回 ER，并每 2 s 尝试 reopen（USB 热插拔）

# serial_bridge.py
while True:
    if ser is None: ser = open('/dev/ttyACM0', 'r+b', buffering=0)  # 失败则 1 s 重试
    r, _, _ = select([sock, ser.fileno()], [], [], 0.2)
    if sock in r: ser.write(sock.recv(4096)); last_rx = now
    if ser.fileno() in r: sock.sendall(ser.read(4096))
    if now - last_rx > 1.5: write_stop_frames(ser); last_rx = now
```

### 5.4 笔记本端改动点（只三处）

1. `new_eye/camera.py` 加 `RemoteCamera`：`read()` 内部发 `RQ`、收 `IM`、`cv2.imdecode` 成 BGR，返回 `(ok, frame)` —— 与现有本地相机接口完全一致，`gui.py` / `main.py` / SAM 流程一行不改。
2. `ghr/10.15/上位机/serial_link.py` 加 `SocketLink`：`open()` 建 TCP 连接、`write()` sendall、`read()` recv+粘包缓存、`describe()` 返回 `TCP 192.168.137.2:5058`；`open_best_link()` 见 `tcp://` 前缀就走它。`host_client.py:101/151/268` 只要求 `open/close/write/read/connected/describe` 六个方法，签名对齐即可。
3. `final/main.py` 加 `--pi HOST`，把 `camera_source` 与 `port="tcp://HOST:5058"` 传下去；不传就还是本地 USB 相机 + COM 口（**默认行为不变，零回归**）。

### 5.5 标定与分辨率（能省一天的关键细节）

- 四点单应保存的是**相机像素坐标**（`new_eye/runtime/calib_marks.json`）→ 若派用**同型号相机、同分辨率 1920×1080**，四点与 `tray_calib.json` 可**直接复用**，不用重标。
- 若为省带宽降到 720p：把四点像素坐标按 `720/1080 = 0.667` 缩放即可；`tray_calib` 的仿射是"归一化 u/v → 脉冲"，分辨率无关（因 `center_tray` 是归一化值）。
- 换镜头/换相机位置 → 必须重做四点标定 + X/Y 标定（验收残差 <100 脉冲，现状 ±3.2 万脉冲，本来就是待办）。

### 5.6 安全与降级

| 故障 | 行为 |
|---|---|
| WiFi 断 | 派看门狗 1.5 s 停车；固件 3 s 心跳停车；恢复后重连、重新 hello/使能 |
| 派死机/断电 | STM32 收不到心跳 3 s 自动停车（只停不关使能） |
| 相机掉线 | 图传返回 `ER`，笔记本提示且不规划动作 |
| 笔记本卡住（SAM 卡 2 s） | 已下发命令正常执行完毕；下一件重新取帧 |
| 网络慢 | 720p + q70 + 只抓 2 帧；必要时只传顶视 |
| 急停 | GUI 既有"停止全部(Esc)"照旧，经桥下发，不依赖派逻辑 |

## 6. 时延/带宽预算（决策依据）

**时延**（已把实测值标出）：

| 环节 | 值 | 来源 |
|---|---|---|
| Pi JPEG 720p | 12–25 ms | 估算（A76 + libjpeg-turbo） |
| WiFi6 上行 720p | 10–40 ms | 估算（1 帧，TCP） |
| SAM-B 单点（GPU 5060） | **800–1000 ms** | 项目现状实测 0.98 fps |
| SAM-B（CPU，参考） | **6.2–6.7 s**（Ryzen 9 8940HX 8 线程） | 本会话实测 → A733 约 20–30 s，故**不可上派** |
| 命令 RTT（经桥） | 8–25 ms | 估算 |
| 运动段 | 1.5–6 s | 机构 |

**带宽**：

| 模式 | 单帧 | 持续 |
|---|---|---|
| 静帧 720p q75 | 90–140 KB | 按需（每件 2–4 帧） |
| 静帧 1080p q80 | 180–260 KB | 按需 |
| 连续 720p@8 JPEG ×2 | ~100 KB | 1.6 MB/s ≈ 13 Mbps（2.4G 吃紧） |
| 连续 1080p@15 JPEG ×2 | ~220 KB | 6.6 MB/s ≈ 53 Mbps（必须 5 GHz） |
| 硬编码 720p@15 H.264 ×2 | — | 3–6 Mbps |

**→ 方案 1 选"按需 720p 静帧"就能把带宽压到 1 Mbps 以下，是稳的。**

## 7. 硬件与接线

- 派供电：**5 V/4–5 A Type-C**（两路 USB 相机同时上电，3 A 会掉压重启）；建议带供电的 USB Hub。
- 相机分配：一台插 USB3.0（蓝口），一台插 USB2.0，避免同控制器带宽争抢；两路都用 MJPG 格式（UVC 压缩，省 USB 带宽）。
- 派↔STM32：**USB 线**（STM32 USB CDC → 派上 `/dev/ttyACM0`），无需电平转换。**这是最省事的路**；备选是 GPIO UART（PA9/PA10 3.3 V），但要改固件。
- ⚠ 前置风险：**固件 USB CDC 从未上板枚举验证**（01 调研结论）→ 到货第一件事就是插派看 `/dev/ttyACM0` 是否出现 + `dmesg`。
- 电源整合（赛项要求单一内置电源不可更换）：建议 4S LiPo（14.8 V）→ 驱动器直供；→ 5 V/8 A DC-DC 供派；→ 5–7.4 V 供舵机；**必须共地**。
- 显示屏（赛项强制）：一期接笔记本 HDMI（GUI 已有 8 页）；二期若要屏挂机器人身上，就用 HDMI 线到派或加一块小屏跑轻量显示程序。

## 8. 验证清单（按顺序做，别跳）

1. **派单独**：装系统 → V4L2 认到两台相机（`v4l2-ctl --list-devices`）→ `capture 720p` 存盘看画面。
2. **派↔STM32**：插 USB → `ls /dev/ttyACM0` → `echo` 发 `0A 6D` 帧看驱动器是否清零反应（或先 `FE` 停车）→ 确认 CDC 枚举 OK。
3. **串口桥（方案 0 降级路径）**：笔记本上位机改 `tcp://pi:5058`，跑 `test_client.py` + GUI 连接 → hello/motor_query 全通（对照现状"四轴 E04"问题是否仍在，这是独立问题）。
4. **图传**：`curl`-式脚本请求 100 帧，统计 p50/p95 时延与丢帧。
5. **整链空跑**：不接驱动器，笔记本走 `--pi` 全流程，看 8 页 GUI 是否与本地模式一致（对比截图）。
6. **半实物**：接 Z 轴 + 夹爪，示教一件，实测节拍。
7. **压测**：连续 12 件，记录每件耗时、无线重连次数、SAM 卡顿。

## 9. 风险表

| 风险 | 影响 | 缓解 |
|---|---|---|
